# 修改与质量修正

统一管理创作过程中的迭代修改与质量修正：创作前信息补全、用户反馈修改、需求变更、条目间一致性冲突修正。

---

## 信息不足

信息缺失时按程度分级处理：

1. 评估缺失程度：核心信息 vs 补充信息
2. **核心信息**（缺失即无法编写条目，如角色名、地名等具体名称）：立即询问用户补充，不可跳过或标记未知
3. **补充信息**：记录到 `创作规划.yaml` 的 `# 待补充` 注释中，在该条目编写前统一询问用户
4. **统一询问时机**：每个条目编写前，先检查是否有待补充信息，一次性询问用户后再编写

## 修改交付方式

修改完成、禁词扫描通过后，按改动范围选择交付方式：

- **小范围改动**（只有世界书，或少量正则/助手脚本）：可只导出改动涉及的那类资源，用户在酒馆侧导入替换即可，不必整卡重出。向用户说明这一选项并询问是否采用；用户同意后用 `export --kind <worldbook|regex|helper>` 导出（命令用法见 `references/manual.md#export`）。世界书按整本导出，用户在酒馆整本替换；正则与助手脚本逐文件导入。
- **大改**（涉及条目结构、开场白、角色卡元数据，或条目间一致性冲突等多段同步修改）：整卡 `pack` 重新输出，用户重新导入整卡。

## 用户反馈不满意

用户对已写条目提出修改意见（"性格不对""外貌太泛""关系不准确"等）。

先询问用户是否还有其他修改要求，收齐全部修改后，统一执行「更新规划→修改条目」。

1. **修正前自检**：若本次修改是由 `check-agent` 扫描报告触发的，先在内部按 `references/rules-check.md` 预演即将改写的内容是否还会命中报告中已发现的违规小节。如命中违规范例，先调整改写方向再落笔，避免越改越差。
2. 定位对应条目，理解用户反馈的具体问题
3. **先更新 `创作规划.yaml`**：将修改后的角色性格、外貌、关系等同步到规划文档的对应字段
4. 按 `references/rules.md` 和该类型的创作规则修正条目内容
5. 修正后重跑禁词扫描（见 `check-agent`）
6. 更新 entryManifest 中该条目的 abstract——abstract 是条目内容的 1-2 句摘要，内容变化后摘要必须同步更新
7. 检查修改是否影响其他条目的一致性（如修改了角色外貌，其他条目中引用外貌的部分是否需要同步）

## 需求变更

中途要加角色、改 MVU 结构、调整条目规划等。若用户连续提出多项变更，先收齐全部变更要求，再统一更新规划并同步修改。

1. 评估影响范围：新需求会影响哪些已完成的条目
2. 更新 `创作规划.yaml`（characters、entries、mvu 等相关段落）
3. 同步修改受影响的已完成条目，修改后按上方"用户反馈"流程处理
4. 如涉及 MVU 结构变更，按 `references/mvu/guide.md#修改流程` 执行变更传播和校验。
   - 更新 EJS 条目内的 getvar 路径（如有 EJS 引用该变量）
   - 运行同步检查命令校验 initvar 与 schema.ts 一致
   - 调 `schema-agent` 修改 schema.ts（schema-agent 会自查同一 `z.object` 内键名唯一）；如 `validate-mvu` / `pack` 报重复字段键错误，处置见 `references/error-handling.md#mvu-校验失败`

## 条目间一致性冲突

DoubleCheck 阶段发现条目间描述矛盾（A 说"与B是敌人"，B 说"与A是挚友"）：

1. 列出所有冲突条目和具体矛盾点
2. 询问用户以哪个为准
3. 根据用户确认结果更新 `创作规划.yaml` 中对应的字段
4. 统一修改相关条目，修改后逐条更新 abstract
5. 重新执行 DoubleCheck 确认无遗留冲突
