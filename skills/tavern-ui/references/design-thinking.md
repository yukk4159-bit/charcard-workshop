# 设计构思

在准备开发环境之后、导入变量结构之前，走一遍设计构思。这一步把故事翻译成视觉与组件决策，向已有的 `cards/{Project}/design-spec.md` 追加 UI 设计段，供后续编码（开发状态栏界面、CSS 色彩变量）消费。

> 设计构思只决定「要什么调性、界面由什么组成」。具体 CSS 配方、动画参数、美化代码是编码阶段的任务，不在本文档范围内。

## 输入

- **`cards/{Project}/design-spec.md`**：叙事设计段已由 tavern-design 产出。读取已有内容，本阶段在文件末尾追加 UI 设计段，不替换叙事段。
- **`schema.ts`**：项目的变量结构。读项目目录里的原文件即可，**先不要复制**到模板——构思阶段若发现需要调整字段（如把 `hp` 拆成 `current_hp/max_hp`），在项目侧改更直接，复制留到导入变量结构一步。
- **创作规划 / 角色卡上下文**：世界观、情绪基调、角色印象、核心冲突。这些是视觉翻译的来源。
- **参考角色卡（可选）**：用户想借鉴某张角色卡的 UI 时提供，见下文「参考已有 UI」。

## 视觉基调

把故事翻译成 UI 的调性。感官词、交互人格、配色三者是一条推导链，不要并列成三张孤立的表。

### 1. 提炼感官词

从世界观、情绪基调、角色印象、核心冲突中提取 3–5 个**感官可感知的**视觉词，而非抽象标签。

| 来源 | 抽象表达 | → 提炼为感官词 |
|------|---------|--------------|
| 世界观氛围 | "现代魔法少女" | 星光、辉光、几何纹样、渐变 |
| 情绪基调 | "青涩纯爱" | 粉白、柔和、圆润、轻微脉动 |
| 情绪基调 | "扭曲占有" | 深紫、锐利、发光、缓慢蚕食 |
| 角色印象 | "青梅竹马的恋人" | 温暖、熟悉、柔软的触感 |
| 核心冲突 | "抵抗→发现→接纳" | 从圆到锐再到融合的过渡 |

抽象标签（"现代""纯爱"）无法直接落到视觉上，必须翻译成感官词（"星光""粉白"）才能指导配色与组件形状。

### 2. 交互人格

把 UI 拟人化：它跟用户说话的方式是什么。有双线叙事的项目，明线与暗线各定义一份。

| 维度 | 明线（日常） | 暗线（侵蚀/冲突） |
|------|------------|-----------------|
| 语速 | 温柔缓慢 | 冷静干脆 |
| 音量 | 轻声细语 | 耳语般清晰 |
| 动作 | 轻轻触碰 | 慢慢收拢 |
| 距离 | 贴近的温暖 | 无处不在的包裹 |
| 回应 | 等你主动 | 早已准备好 |

交互人格描述的是**感觉**，具体的 CSS 参数（过渡时长、缓动曲线、按压幅度）在编码阶段决定，编码时对照感官词选配即可。

### 3. 语义配色

为每个颜色写「为什么」——这个色值在故事里对应什么。语义来源比色值本身重要：色值可以在编码阶段微调，语义理由一旦定了就不该漂。

| 变量 | 色值 | 语义来源 | 用途 |
|------|------|---------|------|
| primary | （待定） | 日常中，角色脸颊微红时的那种温度 | 标题、头像边框、心形图标 |
| background | （待定） | 清晨窗帘透进来的光，照在白色校服上的颜色 | 状态栏背景、消息气泡底色 |
| accent | （待定） | 心跳漏一拍时涌上脸颊的血色 | 好感度数值、重要提醒 |

> 色值在构思阶段可留空待定。色彩变量的**命名规范**（功能语义而非视觉描述）在编码阶段执行，见 SKILL.md 的「CSS 色彩变量命名规范」一节。

## 组件构思

视觉基调定的是调性，组件构思定的是调性如何落到界面的区块上。这是旧流程缺失的层面。

### 1. 信息优先级

基于 `schema.ts` 的字段，排定信息优先级：

- **始终可见**：核心属性 2–3 个（如头像、角色名、好感度/侵蚀度）。这些进折叠状态栏的标题栏。
- **展开可见**：次级数据（能力配置、详细状态、日志）。这些进折叠体。
- **情境可见**：仅在特定变量阈值下出现的元素（侵蚀模式的全屏覆盖、特定事件的通知）。

### 2. 布局模式

五种布局模式，按故事类型选择。具体 CSS 骨架是编码阶段的事，这里只定方向。

| 布局 | 语义 | 适用故事 |
|------|------|---------|
| 叙事型（单列纵向） | 节奏慢，像读日记从上到下浏览 | 校园纯爱、和风妖怪、日常 |
| 展示型（双列网格） | 信息平行，需要快速对比 | TS 转生、异世界、战斗冒险 |
| 仪表型（紧凑多区） | 一切处于监控之中 | 赛博朋克、科技、数据向 |
| 沉浸型（全屏覆盖） | 世界变了，切换时完全不同视觉 | 黑暗幻想、调教侵蚀高潮 |
| 混合型（折叠+网格） | 平常做日常，需要时看细节 | 多数角色卡（推荐默认） |

混合型覆盖约 90% 的需求：标题栏始终可见（头像+名字+核心属性），点击展开能力网格与进度条。

### 3. 组件树草图

用文字或缩进画出界面的区块组成关系。例：

```
状态栏
├─ 标题栏（始终可见）
│  ├─ 头像 + 角色名
│  └─ 核心数值（好感度、侵蚀度）
├─ 展开区（点击标题栏切换）
│  ├─ 能力配置网格
│  ├─ 进度条组（HP/侵蚀度）
│  └─ 日志/最近事件
└─ 情境覆盖层（侵蚀度 > 阈值时覆盖）
```

这张草图是后续编码（拆分 Vue 子组件、规划 `components/` 目录）的直接输入。

### 4. 双线叙事的布局体现

有明/暗线的项目，写明布局在哪会变：

- 哪些区块在两线下结构相同、只换配色（如标题栏）
- 哪些区块在暗线下新增或变形（如侵蚀下多出全屏覆盖层）
- 切换条件（哪个变量、哪个阈值触发）

切换逻辑在编码阶段实现（CSS 条件类、EJS 判断、或 Vue 组件的条件渲染），构思阶段只写明「什么变、何时变」。

## 参考已有 UI

用户指定某张角色卡的 UI 作为参考时，走这条支线。

1. **拿到目标角色卡**（PNG 或 JSON）。
2. **回到 tavern-cards skill**，执行其 `unpack` 命令把角色卡还原成项目目录。还原后，前端界面 HTML 在项目的 `正则/` 目录下（文件名对应原卡的 `regex_scripts[].scriptName`，常见如 `正则/状态栏界面.txt`）。
3. **从还原出的界面文件提取可借鉴的**：布局结构（区块如何组织）、配色调性（用了哪类语义色）、交互手法（折叠/切换/通知怎么做的）。
4. **借鉴的是思路，不是复制代码**。本 skill 走 Vue 3 路线，实现方式与被参考卡可能不同；参考的是「它怎么把故事变成界面」，然后把这种翻译用到自己的 `design-spec.md` 里。
5. 借鉴后回到「视觉基调」与「组件构思」，把参考融入自己的产出，而非把别人的 HTML 搬过来用。

> `unpack` 的完整命令用法、merge/fresh 模式、产出目录结构，见 tavern-cards skill 的 `references/manual.md` 的 unpack 一节。

## 独特性自检

追加 UI 设计段后，回答三个问题：

1. **去色辨识度**：把这个 UI 的色值全部换成灰阶，它还特别吗？布局和交互本身是否有辨识度，还是只靠配色撑场？
2. **唯一元素**：这个 UI 有没有一个元素，是其他同类型角色卡绝不会有的？（故事独有的机制 → UI 上独特的呈现）
3. **过渡是否讲故事**：每个交互反馈是在「告知用户」还是在「讲一个故事」？每次过渡是否在推进用户与角色/世界的关系？

三个问题答不上来，回到前面的环节补：感官词太泛就重提炼，布局选了通用模式就问故事是否需要独特结构，交互只是状态切换就问能否赋予叙事含义。
